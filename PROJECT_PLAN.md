# dashsync — план разработки

**Что это за документ.** Полное описание проекта: что строим, на чём, в каком порядке, как учимся Go по ходу дела и как ведём разработку через Claude Code. Документ рассчитан на то, чтобы его целиком положить в корень репозитория и передать в Claude Code как контекст — раздел 12 содержит готовый стартовый `CLAUDE.md` и первый промпт.

**Исходные данные.** Основан на исследовании от 07.09.2026: ниша частично занята (homepagectl, Go, ~203★), базовый сценарий закрыт встроенным label-discovery у Homepage/Glance, Homarr v1+ на БД и из скоупа исключён. Дифференциация — **идемпотентный git-native мультиформатный синк**, а не «ещё один генератор».

## 1. Продукт

### 1.1. Одна фраза

CLI-инструмент, который превращает запущенные Docker-контейнеры в статические конфиги self-hosted дашбордов (Homepage, Dashy, Homer), синхронизирует их идемпотентно и не затирает то, что ты правил руками.

### 1.2. Что делает (в порядке приоритета)

1. **Читает** Docker API (несколько хостов, Swarm) → нормализованная модель сервисов.
2. **Рендерит** её в несколько форматов конфигов из одного источника истины.
3. **Мержит** результат в существующий файл: добавляет новое, обновляет изменённое, **удаляет осиротевшее**, сохраняет ручные правки и комментарии.
4. **Показывает diff** до записи (`--dry-run` по умолчанию в CI-режиме).
5. **Детерминирован**: два запуска подряд без изменений в Docker → нулевой diff. Вывод коммитится в git.

### 1.3. Чего НЕ делает (non-goals, фиксируем сразу)

- Не веб-UI. Не демон с базой. Не Kubernetes (может быть, потом — но не в v1).
- Не Homarr (у него БД, генерировать нечего — только упоминание в README как «future work via API»).
- Не заменяет встроенный runtime-discovery Homepage — работает **параллельно** с ним для тех, кто хочет статический конфиг в git.
- Не деплоит, не рестартит контейнеры, не пишет ничего в Docker. **Read-only по отношению к Docker. Всегда.**

### 1.4. Ключевая инженерная идея: managed markers

Это то, что отличает проект от одноразового генератора и то, что интересно обсуждать на собеседовании.

Проблема: у пользователя `services.yaml` наполовину сгенерирован, наполовину написан руками, с комментариями. Как обновить только «свою» часть?

Решение — маркировка владения. Каждая сгенерированная запись помечается:

```yaml
- Media:
    # dashsync:managed id=sha256:abc123 host=homelab-1
    - Jellyfin:
        href: http://10.0.0.5:8096
        icon: jellyfin
    # /dashsync
    - Мой ручной сервис:      # ← не тронем никогда
        href: https://example.com
```

Отсюда вытекает вся сложность и вся ценность:

- нужен **YAML-AST**, а не `Unmarshal → Marshal` (последний убивает комментарии и порядок ключей);
- нужен **трёхсторонний merge**: desired (из Docker) × managed (что мы писали в прошлый раз) × actual (что в файле сейчас);
- нужна **стратегия конфликтов**: пользователь поправил поле внутри managed-блока — уважаем или перезаписываем? (Решение: конфигурируемо, по умолчанию `preserve` с предупреждением.)

Аналог-эталон: AutoKuma (Rust, ~850★) делает ровно это для Uptime Kuma. Смотри его как источник паттернов, не как конкурента.

## 2. Архитектура

### 2.1. Поток данных

```
Docker API ─┐
            ├─→ [discovery] ─→ []RawContainer ─→ [mapper] ─→ []Service ─┐
Docker API ─┘                                    (+ labels,             │
 (host N)                                         + overrides)          │
                                                                        ▼
                        ┌──────────────────────────────────── [renderer registry]
                        │                                              │
              homepage.Renderer          dashy.Renderer          homer.Renderer
                        │                        │                     │
                        └────────────→ [merger] ←┴─────────────────────┘
                                          │
                          existing file ──┤
                                          ▼
                                 [diff] → [writer] → файл на диске
```

Ключевое свойство: **каждая стрелка — чистая функция**. Ввод-вывод (Docker, файлы) живёт только на краях. Это делает 90% кода тестируемым без Docker и без файловой системы — что и есть главный аргумент на код-ревью.

### 2.2. Структура репозитория

```
dashsync/
├── cmd/dashsync/main.go          # только парсинг флагов и вызов cli.Run
├── internal/
│   ├── cli/                      # cobra-команды: inspect, sync, diff, version
│   ├── config/                   # чтение dashsync.yaml, валидация, дефолты
│   ├── discovery/
│   │   ├── docker.go             # обёртка над docker client
│   │   ├── labels.go             # парсинг dashsync.* labels
│   │   └── discovery_test.go
│   ├── model/                    # каноническая модель: Service, Group, Widget
│   ├── render/
│   │   ├── renderer.go           # интерфейс Renderer
│   │   ├── homepage/
│   │   ├── dashy/
│   │   └── homer/
│   ├── merge/                    # YAML-AST merge, managed markers ← сердце проекта
│   └── diff/                     # человекочитаемый вывод изменений
├── testdata/                     # golden-файлы, фикстуры Docker-ответов
├── docs/
├── .github/workflows/
├── .golangci.yml
├── .goreleaser.yaml
├── CLAUDE.md
├── PROJECT_PLAN.md               # ← этот файл
├── LICENSE                       # MIT или Apache-2.0, выбрать в M0
└── README.md
```

Почему `internal/` — потому что пока нет обязательств по публичному API. Если позже кто-то попросит библиотеку, вынесешь в `pkg/`. Наоборот сделать нельзя.

### 2.3. Центральные абстракции (спроектируй их сам, это твоя работа, не Claude)

```go
// Каноническая модель — намеренно НЕ повторяет ни один из форматов дашбордов
type Service struct {
    ID          string            // стабильный: hash(host + container name)
    Name        string
    Group       string
    URL         string
    Icon        string
    Description string
    Extra       map[string]any    // формат-специфичное, из labels
    Source      Source            // откуда пришёл: какой хост, какой контейнер
}

type Renderer interface {
    Name() string                              // "homepage"
    Render(groups []Group) (*yaml.File, error) // AST, не строка
    DefaultPath() string                       // "services.yaml"
}

type Merger interface {
    Merge(existing, generated *yaml.File, opts MergeOptions) (*yaml.File, []Change, error)
}
```

Три интерфейса — этого достаточно. Не плоди абстракции заранее.

## 3. Технологический стек

Критерий отбора: **зрелость и предсказуемость**, а не новизна. Каждая позиция — либо стандартная библиотека, либо то, на чём стоит половина cloud-native экосистемы.

| Слой | Выбор | Почему именно это |
|---|---|---|
| Язык | Go, актуальная стабильная версия (проверь go.dev/dl) | Цель обучения; на нём написаны Docker, k8s, Terraform, Prometheus |
| Управление версией Go | `go.mod` с явной директивой `go 1.xx` | Воспроизводимость сборки |
| CLI-фреймворк | `github.com/spf13/cobra` | Де-факто стандарт (kubectl, docker, gh); субкоманды, help, completion из коробки |
| Конфиг | своя структура + `goccy/go-yaml` + флаги cobra | **Осознанно без Viper**: он тянет много зависимостей и магии; для одного конфиг-файла это оверкилл |
| YAML | `github.com/goccy/go-yaml` | `gopkg.in/yaml.v3` архивирован (апрель 2025); goccy даёт доступ к AST и комментариям — без этого merge невозможен |
| Docker | `github.com/docker/docker/client` | Официальный SDK. Инициализация: `client.NewClientWithOpts(client.FromEnv, client.WithAPIVersionNegotiation())` |
| Логирование | `log/slog` (stdlib) | Ноль зависимостей, структурные логи, есть с Go 1.21 |
| Ошибки | stdlib `errors` + `fmt.Errorf("%w")` | Без внешних библиотек; sentinel errors + `errors.Is/As` |
| Тесты | stdlib `testing` + `github.com/google/go-cmp` | Table-driven тесты — идиома Go; go-cmp даёт читаемые diff'ы в ассертах |
| Golden-файлы | самописный хелпер + флаг `-update` | 20 строк кода, полный контроль; идеально ложится на «рендер → ожидаемый YAML» |
| Интеграционные тесты | `testcontainers-go` (только с M4, опционально) | Поднимает реальный Docker для e2e; до M4 хватает фикстур |
| Линтер | `golangci-lint` | Стандарт индустрии; конфиг в `.golangci.yml` в репо |
| Уязвимости | `govulncheck` (`golang.org/x/vuln`) | Официальный инструмент Go-команды |
| Релизы | `goreleaser` | Кросс-компиляция + GitHub Releases + Docker-образы одной командой |
| CI | GitHub Actions | `actions/setup-go`, `golangci-lint-action`, `goreleaser-action` |
| Зависимости | Dependabot (`.github/dependabot.yml`) | Автообновления Go-модулей и actions |
| Контейнер | multi-stage Dockerfile, distroless или scratch | Статический бинарь Go → образ в единицы МБ, без shell |

**Правило зависимостей проекта:** новая внешняя библиотека добавляется только после ответа на вопрос «что именно в stdlib этого не умеет и сколько строк я сэкономлю». Для инфра-тулзы 6–8 прямых зависимостей — норма, 40 — красный флаг на ревью.

## 4. Учебный трек по Go

Ты опытный инженер, поэтому не нужен курс «что такое цикл». Нужны **отличия Go от того, что ты уже знаешь**, и идиомы, по которым на ревью отличают человека, который пишет на Go, от человека, который пишет на Python синтаксисом Go.

### 4.1. Обязательный минимум перед первой строкой (2–4 часа)

- **A Tour of Go** — пройди целиком, особенно разделы про методы, интерфейсы, горутины (`go.dev/tour`).
- **Effective Go** — читай как справочник, не запоминай.
- **Go Proverbs** (Rob Pike) — 20 минут видео, задаёт способ мышления.

### 4.2. Темы по этапам проекта

Учить не «весь Go», а ровно то, что нужно на текущем этапе. Порядок не случайный.

| Этап | Темы Go | Почему здесь |
|---|---|---|
| **M0** | `go mod`, структура проекта, `go test`, `gofmt`, встроенные типы, slices vs arrays, maps | Не начнёшь без этого |
| **M1** | Структуры, методы, указатели vs значения, `error` как значение, `%w`-обёртки, `errors.Is/As`, контексты (`context.Context`) | Docker SDK весь на контекстах и ошибках |
| **M2** | **Интерфейсы** (неявная реализация, «принимай интерфейсы, возвращай структуры»), embedding, table-driven тесты, `t.Run`, golden-файлы | Renderer — твой первый настоящий интерфейс |
| **M3** | Рекурсия по деревьям, работа с AST, `sort.Slice` и детерминизм, generics (осторожно, по необходимости) | YAML-AST merge — самая сложная часть |
| **M4** | **Горутины, каналы, `sync.WaitGroup`, `errgroup`**, отмена через контекст | Опрос нескольких Docker-хостов параллельно — естественный повод выучить конкурентность на реальной задаче, а не на выдуманной |
| **M5** | `//go:embed`, build tags, ldflags для версии, кросс-компиляция | Упаковка |
| **M7** | Каналы для events-стрима, graceful shutdown по сигналу | Watch-режим |

### 4.3. Идиомы, которые проверяют на ревью

Выпиши это на отдельный листок и сверяйся:

1. Ошибки не паникуют. `panic` только в `main` при невосстановимой конфигурации.
2. `if err != nil { return fmt.Errorf("контекст: %w", err) }` — контекст добавляется на каждом уровне.
3. Интерфейсы объявляются **на стороне потребителя**, а не рядом с реализацией.
4. Маленькие интерфейсы. Один-два метода. `io.Reader` — эталон.
5. `context.Context` — всегда первый параметр, никогда не в структуре.
6. Экспортируется только то, что действительно нужно снаружи. Заглавная буква — это решение, а не привычка.
7. Никаких `interface{}`/`any` там, где можно назвать тип.
8. Горутина всегда имеет понятный момент завершения. Утечка горутины — баг.
9. Тесты — table-driven, с `t.Parallel()` там, где это безопасно.
10. Нет глобального состояния. Зависимости передаются явно.

### 4.4. Как проверять, что ты действительно выучил

В конце каждого этапа — **самотест**: закрой Claude Code и объясни вслух (или запиши в `docs/decisions/`), почему код устроен именно так. Если не можешь объяснить — ты этот кусок не написал, а принял. Вернись и перепиши.

## 5. Процесс разработки через Claude Code

### 5.1. Установка и базовая настройка

Claude Code ставится как npm-пакет `@anthropic-ai/claude-code`; актуальные инструкции — на `code.claude.com/docs`. Проверь там же требования к окружению, они меняются.

Что настроить в первый день:

- `CLAUDE.md` в корне репозитория (готовый — в разделе 12).
- `.claude/settings.json` — правила разрешений: что Claude может запускать без спроса (`go test`, `go build`, `golangci-lint`), а что требует подтверждения (`git push`, `rm`, любые сетевые вызовы).
- Всё это **коммитится в репозиторий** — это часть проекта, а не локальная настройка.

### 5.2. Ключевые механики, которые надо использовать с первого дня

| Механика | Зачем тебе |
|---|---|
| **Plan mode** (Shift+Tab) | Claude читает код и предлагает план, **не трогая файлы**. Всегда начинай с него для любой задачи сложнее опечатки |
| **CLAUDE.md** | Правила проекта; держи под ~200 строк, иначе перестаёт работать |
| **Checkpoints / `/rewind`** | Откат сессии и правок к предыдущей точке — страховка при экспериментах |
| **Subagents** (`.claude/agents/`) | Отдельный агент-ревьюер с read-only инструментами: ревьюит твой код, не может его править |
| **Hooks** (`.claude/hooks/`) | Правила, которые **исполняются кодом**, а не «просятся» в промпте. Например: перед каждым коммитом прогнать `gofmt` и `go test` |
| **Skills** | Оформи повторяющиеся процедуры проекта (релиз, добавление нового рендерера) как skill |
| **`/context`, `/compact`** | Следи за контекстом; на длинных сессиях сжимай, а не надейся |

### 5.3. Протокол «учусь, а не получаю готовое»

Это самая важная часть раздела. Три режима работы, переключайся сознательно:

**Режим A — «Объясни, я напишу» (по умолчанию для основной логики).**
Claude объясняет подход, показывает идиому на *другом* примере, пишет тест — реализацию пишешь ты. Затем Claude ревьюит.
Применять для: `internal/merge`, `internal/model`, `internal/render/*` — всё, что составляет ценность проекта.

**Режим B — «Напиши, я разберу» (для бойлерплейта).**
Claude пишет, ты читаешь построчно и задаёшь вопросы по каждой непонятной конструкции, пока не сможешь объяснить целиком.
Применять для: cobra-команды, CI-workflow, Dockerfile, GoReleaser-конфиг.

**Режим C — «Свободные руки» (только для рутины).**
Claude делает без построчного разбора.
Применять для: переименования, форматирование, обновление зависимостей, генерация тестовых фикстур.

Правило: **если файл лежит в `internal/merge` или `internal/model` — только режим A.** Это не бюрократия, это то, что ты будешь показывать на собеседовании.

### 5.4. Цикл работы над одной задачей

```
1. Задача из roadmap → пишешь issue в GitHub (сам, своими словами)
2. Claude Code, plan mode: "прочитай PROJECT_PLAN.md и код, предложи план для issue #N"
3. Читаешь план. Спорь. План должен помещаться в голове
4. Пишете тест первым (Claude может, режим B)
5. Реализация — по режиму A/B/C в зависимости от пакета
6. go test ./... && golangci-lint run — зелёное
7. Просишь субагента-ревьюера: "разнеси этот диф, найди то, что не выдержит ревью"
8. Исправляешь. Коммит с осмысленным сообщением
9. Раз в этап: записываешь ADR в docs/decisions/ (сам, от руки)
```

Пункт 7 не пропускай. Формулировка «найди проблемы, не хвали» работает сильно лучше, чем «проверь код».

### 5.5. Гигиена git

- Conventional commits (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`) — потом бесплатно получишь changelog из GoReleaser.
- Ветка на задачу, PR даже в свой репозиторий: у тебя останется история ревью, которую можно показать.
- **Мелкие коммиты.** Коммит «реализовал merge» на 900 строк — это то, чего боится каждый ревьюер.

## 6. Дорожная карта

Оценки — для формата «вечера и выходные», с учётом того, что Go новый. Умножай на свой коэффициент честности.

### M0 — Фундамент (3–5 дней)

**Цель:** пустой, но полностью настроенный репозиторий, который уже собирается в CI.

- [ ] Go установлен, `A Tour of Go` пройден
- [ ] Репозиторий, лицензия (MIT или Apache-2.0 — выбери и обоснуй в README), `.gitignore`
- [ ] `go mod init github.com/<user>/dashsync`
- [ ] `cmd/dashsync/main.go` — cobra, команда `version`, версия через ldflags
- [ ] `.golangci.yml`, `go test ./...` (пусть один тривиальный тест)
- [ ] GitHub Actions: build + test + lint на push и PR
- [ ] `CLAUDE.md`, `.claude/settings.json` закоммичены
- [ ] `PROJECT_PLAN.md` в репо

**Definition of Done:** зелёный CI-бейдж в README на пустом проекте. Дальше он никогда не должен краснеть.

**Учебный чекпоинт:** объясни, зачем нужен `go.sum` и что произойдёт, если его удалить.

### M1 — Discovery, read-only (1 неделя)

**Цель:** `dashsync inspect` показывает контейнеры и распознанные labels. Ничего никуда не пишет.

- [ ] Подключение к Docker через `FromEnv` + `WithAPIVersionNegotiation`
- [ ] Список контейнеров, чтение labels
- [ ] Схема labels: `dashsync.enable`, `dashsync.name`, `dashsync.group`, `dashsync.url`, `dashsync.icon`, `dashsync.<renderer>.<key>` — **спроектируй сам, это дизайн-решение, запиши ADR**

## 7. CI/CD

### 7.1. Пайплайн на PR

```yaml
# .github/workflows/ci.yml — концепт, точный синтаксис пусть напишет Claude в режиме B
jobs:
  test:      # go test ./... -race -coverprofile
  lint:      # golangci-lint-action
  build:     # go build под несколько GOOS/GOARCH
  vuln:      # govulncheck ./...
```

Обязательно:

- **`-race` в тестах** — с M4 это не опция, а необходимость.
- **Матрица версий Go**: текущая и предыдущая минорная.
- **Кэш модулей** через `actions/setup-go` (`cache: true`).
- **Ветка `main` защищена**: PR обязателен, CI обязателен зелёный.

### 7.2. Релиз

Тег `vX.Y.Z` → GoReleaser собирает бинари, checksums, Docker-образы, changelog из conventional commits. Ничего вручную.

### 7.3. Безопасность цепочки поставок

- Пиннить GitHub Actions по SHA, не по тегу.
- `permissions:` в workflow — минимальные, явно заданные.
- Dependabot на `gomod` и `github-actions`.
- Опционально: SBOM через GoReleaser, подпись релизов через cosign — сильный пункт для инфра-резюме.

## 8. Безопасность (это инфра-тулза, тут судят строго)

| Риск | Решение в проекте |
|---|---|
| Доступ к `/var/run/docker.sock` = root на хосте | В доках **основной** рекомендуемый способ — `tecnativa/docker-socket-proxy` с `CONTAINERS=1`, `POST=0`. Прямой сокет — только read-only bind-mount и с явным предупреждением |
| Инструмент может что-то сломать в Docker | Архитектурно используем только read-эндпоинты. Задокументировать это явным списком вызываемых API |
| Секреты в конфиге дашборда | Никогда не переносить значения env-переменных контейнера в вывод. Только явные labels. Записать как правило безопасности в доках |
| Затирание пользовательского файла | Атомарная запись, `.bak`, `--dry-run` по умолчанию в неинтерактивном режиме |
| Запуск от root в контейнере | Distroless + non-root USER |
| Уязвимые зависимости | `govulncheck` в CI, Dependabot |

Раздел `SECURITY.md` в репозитории — обязателен. Это дёшево и это видно.

## 9. Тестирование

| Уровень | Что покрывает | Инструменты |
|---|---|---|
| Юнит | Парсинг labels, маппинг в модель, сортировка, рендеринг | stdlib `testing`, table-driven, `go-cmp` |
| Golden | Модель → YAML для каждого формата | `testdata/golden/*.yaml`, флаг `-update` |
| Merge-сценарии | Все комбинации existing × generated | Фикстуры файлов в `testdata/merge/` |
| Интеграционные | Реальный Docker | `testcontainers-go`, тег `//go:build integration` |
| Ручной smoke | Работает ли конфиг в живом дашборде | Твой homelab |

Целевое покрытие: не гонись за процентом, но `internal/merge` и `internal/render` должны быть покрыты плотно — это то, куда ревьюер посмотрит первым делом. Метрику покрытия выводи в CI, но не превращай её в KPI.

Отдельно: **тест на идемпотентность** как явный тест. `sync` дважды на одном входе → второй запуск возвращает пустой список изменений. Это исполняемая спецификация главного свойства продукта.
